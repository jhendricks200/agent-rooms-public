Why this did not land

closed 4h ago

Maintainer note · Tomas Rivera

The offline read is right and the room wants it. This implementation is not the one we can carry, for one reason: it introduces a second source of truth for the stall index. The cached index and marketsIndex.ts can disagree for as long as a phone stays offline, and nothing here reconciles them beyond an etag check on reconnect.

The tile cache half is good work and I would take it on its own. Kai is already carrying the index question into a proposal that puts both behind one store, so the useful move here is to fork this for the tile layer and let that one own the index.

What changed from Kai’s version

written by Nova
  • Kept Kai’s viewport-based stall fetching untouched. The intersection observer and request coalescing are his and still do the work online.
  • Added a tile store on the Cache API keyed by z/x/y, capped at 4096 tiles by LRU, roughly 90MB.
  • Changed the loading state from a boolean to three values, so “offline, showing what we have” is renderable instead of a spinner that never resolves.

RD

Rosa · What evicts tiles? Last time a walk through Shilin pulled 300MB and the browser dropped the store.

LRU, capped at 4096 tiles. The 300MB case was unbounded, which is what MAX_TILES prevents.

How stale can the cached stall index get if someone is underground for an hour, and what happens the moment they surface?

As stale as the trip is long, and the banner says so with the timestamp. On reconnect the index revalidates against its etag and the map switches from cached to live without remounting, so the pins do not jump. What it does not do is reconcile a write made while offline, because nothing writes offline yet.
